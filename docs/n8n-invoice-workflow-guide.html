n8n Invoice Workflow Guide

How to build and test your own supplier-invoice extraction workflow using the webhook contract already present in the staff page.

The workflow is not created or enabled by this guide.
Use synthetic/test invoices until the security boundary is hardened.

1. What exists today

The staff page admin-invoice-ai.html uploads PDF and image files to the private supplier-invoices Storage bucket (maximum 15 MB), inserts a row in supplier_invoices, and displays the saved invoice status. If the optional URL is configured, staff can trigger the webhook when uploading or re-send an invoice from the invoice list.

The URL is read from window.BC_CONFIG.N8N_INVOICE_WEBHOOK_URL in config.js. It is intentionally blank in this project. The browser sends the following JSON body:

{
  "event": "supplier_invoice.uploaded",
  "invoice_id": "UUID",
  "file_name": "supplier-invoice.pdf",
  "content_type": "application/pdf",
  "download_url": "short-lived signed URL"
}

Before sending, the page creates a signed URL valid for 600 seconds and changes the row status to processing. A successful HTTP response only means n8n accepted the request; n8n must still download, extract, validate, and update the database row. The UI expects the workflow to write extraction fields and eventually set the status to processed or failed.

Production security: This is a static website. A webhook URL placed in config.js is visible to every visitor. Do not put an n8n password, API key, Supabase service-role key, or other secret in that file. Do not connect a public unauthenticated production webhook directly to unrestricted database writes.

2. Build the first workflow in n8n

Start in an n8n development instance with a test webhook and non-sensitive sample invoice. Node names differ slightly between n8n versions; use the equivalent node/action in your installation.

  1. Webhook trigger: create a POST webhook that accepts JSON. Configure a test URL first, use a unique non-guessable path, and enable the strongest authentication available for your deployment. Set response mode so the browser receives a prompt acknowledgement (HTTP 2xx) after the workflow has safely accepted the job, not after a long OCR run.
  2. Validate request: require event === "supplier_invoice.uploaded", a valid invoice UUID, and an HTTPS download_url. Reject missing/invalid fields. Apply size/type limits at the processing layer too.
  3. Fetch the document promptly: use an HTTP Request node to GET download_url as binary data. The signed link expires after 10 minutes. Do not log the full URL or place it in public execution logs longer than needed.
  4. Extract text/fields: pass the binary file to your chosen OCR/document extraction service or self-hosted parser. Normalize the provider response into the agreed JSON format below. Treat OCR as untrusted input; amounts, dates, currency, supplier, and invoice number require validation.
  5. Validate results: verify the invoice ID belongs to an expected queued/processing record; validate numeric totals and date formats; reject impossible values. Use an idempotency strategy so retrying the same invoice does not create duplicate accounting entries.
  6. Update Supabase securely: use a server-side credential in n8n's encrypted credential store or a narrowly scoped server-side relay. Update only the matching supplier_invoices row by id; set the extracted fields, JSON payload, status, and updated_at.
  7. Error branch: on download, OCR, validation, or database failure, set status to failed and write a short safe error_message. Do not include secrets or the signed URL in that message. Keep retry behavior bounded.
Recommended node chain: Webhook → Validate/authenticate → Fetch invoice binary → OCR/extract → Normalize and validate → Supabase update → Acknowledge. Add an error branch that records failure and supports a controlled retry.

3. Database fields and result shape

The supplier_invoices table already has fields intended for extracted results. Use the existing column names and preserve the original file and metadata:

ColumnUseExample
supplier_nameSupplier or vendor name found in document."Sample Wholesale Ltd"
invoice_numberSupplier's invoice identifier."INV-2026-001"
invoice_date, due_dateISO date values or null when uncertain."2026-06-14"
currencyThree-letter currency code. The default is NGN; do not silently assume it if the document says otherwise."NGN"
subtotal, tax, totalValidated numeric amounts. Preserve correct decimal precision.125000.00
extracted_dataOptional normalized JSON with line items, confidence, and source notes.JSON object
statusSet to processed only after successful validation; use failed when processing cannot complete."processed"
error_messageShort safe explanation on failure; clear it after successful processing.null
updated_atUTC timestamp for the latest processing attempt.ISO timestamp

Example normalized extraction object for extracted_data:

{
  "schema_version": 1,
  "supplier_name": "Sample Wholesale Ltd",
  "invoice_number": "INV-2026-001",
  "invoice_date": "2026-06-14",
  "due_date": null,
  "currency": "NGN",
  "subtotal": 125000.00,
  "tax": 0.00,
  "total": 125000.00,
  "line_items": [
    { "description": "Sample item", "quantity": 10, "unit_price": 12500.00, "line_total": 125000.00 }
  ],
  "confidence": 0.94,
  "needs_human_review": false
}

This result shape is a recommendation for your workflow; it is not a request body currently sent by the website. Do not mark an invoice processed merely because OCR returned text.

4. Secure the browser-to-n8n boundary

Why a direct webhook URL is not a production secret

Anyone can inspect a static site's JavaScript and network requests. If the frontend calls a webhook directly, a URL token, basic-auth secret, or custom credential shipped with the page can be copied and replayed. CORS is not authentication. A random webhook path reduces casual discovery but does not establish authorization.

Recommended production pattern

  1. The signed-in staff browser requests invoice processing from a server-side Supabase Edge Function or equivalent trusted API.
  2. The server validates the Supabase user JWT and checks the user's profiles.role is staff or owner.
  3. The server retrieves the invoice record by ID, checks its storage path and state, and creates a short-lived download URL or streams the file to the automation service.
  4. The server authenticates to n8n using a secret stored only in server-side environment/secret storage, or n8n pulls a signed job from the server.
  5. n8n writes results using a narrowly controlled server-side credential. Restrict its permissions to supplier invoice updates and never expose service-role credentials to the browser.
Keep trust boundaries separate: n8n's server-side credential is for n8n/server code only. The frontend remains on the public Supabase client and RLS. Avoid granting the browser unrestricted invoice updates merely to make a workflow work.

Current integration caveats

  • The current admin page expects a direct HTTP POST to the webhook URL; it does not send an authorization header or signature.
  • The invoice record's RLS allows staff reads/inserts/updates, so a browser user with staff credentials can directly update those allowed fields. Keep staff accounts tightly controlled and consider narrower update policies/a server-only update path before production extraction.
  • inject-env.js currently writes Supabase URL/key only; it does not inject N8N_INVOICE_WEBHOOK_URL. A Netlify build may remove a manually set webhook URL from the generated browser config.
  • The signed URL is usable by whoever obtains it until it expires. Avoid sharing it in logs, notifications, or support tickets.

5. Test, troubleshoot, and operate

Safe test checklist

  1. Use n8n's test webhook URL and a non-production Supabase project or isolated test invoice.
  2. Upload a synthetic PDF/image with no personal, bank, or supplier-sensitive data.
  3. Inspect the webhook body. Confirm the event name, invoice ID, content type, and signed URL are present; do not paste the URL into public logs.
  4. Download the file promptly. Confirm it is valid binary content and respects size/type limits.
  5. Test both a clean extraction and deliberate failures (bad URL, unsupported content, OCR timeout, malformed totals).
  6. Confirm the database row transitions from queued to processing to processed or failed, and that the staff page displays the result.
  7. Test duplicate webhook delivery. It should not create duplicate invoice records or repeated accounting side effects.
  8. Only after security review, switch to a production webhook/relay and apply limits, monitoring, retention, and alerting.
SymptomLikely check
Button says workflow not connectedThe URL is blank in the browser configuration. Build/config changes alone do not create an n8n workflow.
Upload fails before webhookCheck signed-in staff role, bucket name, Storage policies, allowed MIME type, 15 MB limit, and supplier_invoices RLS.
n8n receives request but no extracted values appearCheck workflow database update, matching invoice UUID, row status, required column names, and execution errors.

Webhook works in test but not productionCheck the active URL, n8n activation, HTTPS/network access, authentication boundary, hosting-generated config, and CORS/network errors.
Before processing real invoices: Define who may access invoices, retention/deletion rules, OCR provider data handling, error alerting, retry limits, and a human review process for low-confidence or mismatched totals.

This guide intentionally leaves n8n workflow creation to the project owner. It does not include credentials or claim that OCR, external providers, or production n8n are configured.
