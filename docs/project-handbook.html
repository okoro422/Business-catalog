1. Project at a glance

Business Catalog is a mobile-first online catalogue and ordering application for cosmetics, toiletries, and wholesale supply. It is designed around the Nigerian Naira (NGN) and delivery zones configured in Supabase.

2. How the application is organized

  1. A browser opens a static HTML page from the site host.
  2. The page loads Supabase JS v2, the public browser configuration, and shared client/auth/backend code.
  3. The browser uses the signed-in Supabase session for customer or staff requests. Public catalogue reads use the public client.
  4. Postgres RLS policies enforce which rows the signed-in user may read or change. Key operations such as placing orders and changing credit balances use database functions.
  5. Private uploads are stored in Supabase Storage and accessed using authenticated policies or short-lived signed URLs.
  6. When a webhook URL is configured, the invoice screen sends invoice metadata and a short-lived file URL to n8n.

3. Store and staff features

Customer experience

  • Browse and search products, view richer product information, availability, and configured wholesale tiers.
  • Maintain a cart and submit an order after signing in; database logic validates stock and recalculates the price.
  • Review orders, order details, receipts, and submit a cancellation or return request.
  • Save products, manage the account, request wholesale quotations, accept an eligible quote, and view notifications or support messages.

Staff experience

  • Manage products, categories, delivery zones, orders, customer records, reports, staff, and activity.
  • Review supply requests and create quotations; accepted, priced quotes can be converted to orders.
  • View and update a customer credit account through staff-only database functions with a ledger trail.
  • Upload supplier invoices to private storage, inspect their status, and optionally dispatch them to n8n for extraction.

Checkout and payment status

The checkout supports the stored payment-method values online, cash, and transfer. The order RPC creates an order with payment status pending. A payment gateway, card charging flow, and automated payment verification are not implemented in the inspected checkout. Do not treat selecting “online” as proof that a payment was collected.

Important database functions

  • place_order(...) validates items and stock, reads current prices and wholesale tiers, computes delivery, decrements stock, and creates the order.
  • submit_supply_request(...) validates a signed-in customer's business request and its line items.
  • convert_supply_quote_to_order(...) converts the signed-in customer's eligible quote to an order once and stores the resulting order ID.
  • staff_manage_customer_credit(...) creates or updates a credit limit and enabled state after checking staff access.
  • staff_adjust_credit_balance(...) changes a credit balance only for staff, checks the limit/balance, and writes a ledger entry.

RLS is enabled in the base schema. Catalogue data is readable publicly where allowed; customers generally access their own records; staff policies use is_staff() to allow staff/owner access. Private invoice and request files use separate buckets and Storage policies.

Owner setup: After registering and confirming the account, an authorized project owner must promote the first staff account using the profile update instruction in the SQL comments. Protect this access carefully; never promote an account based only on an unverified email supplied by a user.

5. Initial setup and SQL installation

For a brand-new Supabase project

  1. Create a Supabase project and keep its database password private.
  2. In Supabase, open SQL Editor and run supabase-schema.txt once to create the base tables, policies, functions, image bucket, and sample catalogue.
  3. Run supabase-fixes.sql to apply the additive profile/product/chat and checkout updates.
  4. Run supabase-remaining-features.sql to add credit ledger, private invoice/request uploads, quote conversion, and related policies/functions.
  5. Review the SQL Editor results for errors before proceeding. Verify that the expected tables, functions, and Storage buckets exist.
  6. Set the site's Supabase URL and publishable/anon key in the browser configuration or deployment environment.
  7. Register a customer account, confirm email if confirmation is enabled, and promote the intended first owner using a trusted admin-controlled SQL session.
  8. Sign in as that owner and verify the staff area. Test as a separate customer account as well.

For an existing project

Do not rerun the fresh-install base schema over populated production data. Back up the database, inspect the current schema, then apply only the missing migrations in order: supabase-fixes.sql, followed by supabase-remaining-features.sql. Confirm that the starting schema is compatible and review each migration result.

SQL source of truth: The repository's three SQL files are separate steps, not interchangeable alternatives. The base schema contains sample records and initial policies. Never run SQL copied from an outdated handover document instead of checking the current files.

Authentication settings

In Supabase Auth, configure the site URL and allowed redirect URLs for the exact local and production origins you use. Decide whether email confirmation is required, configure SMTP for real customer mail, and test password recovery/confirmation flows. Do not assume a redirect works until tested on the published hostname.

6. Configuration and deployment

Local/browser configuration

The current config.js defines SUPABASE_URL, SUPABASE_ANON_KEY, and an intentionally empty N8N_INVOICE_WEBHOOK_URL. Use the project's Supabase publishable (or legacy anon) key only. Keep the Supabase service-role key and all server credentials out of the repository and browser.

Netlify

netlify.toml runs node inject-env.js and publishes the repository root. Add the expected Supabase URL and public-key environment variables in the Netlify site settings. The current injection script writes Supabase public config but does not preserve or inject the n8n webhook URL. A build may replace a manually edited config file; verify the generated deployment config before testing. For production invoice automation, prefer a secured server-side relay instead of exposing an n8n endpoint in frontend code.

GitHub Pages or another static host

The pages are root-level static files and do not require a frontend bundle. Configure the public Supabase values in config.js, publish the correct root folder, and test all relative links at the actual repository subpath/hostname. Static hosting does not make browser configuration private. The included GITHUB_PAGES.txt and HANDOVER_PROMPT.txt describe an older layout in places; use the current repository file list and scripts as the source of truth.

7. Routine operation and testing

Recommended test sequence

  1. Open the deployed store over HTTPS and confirm that the catalogue loads from Supabase without console/network errors.
  2. Register a new retail customer and a business customer; verify profile creation and email-confirmation behavior.
  3. As a normal customer, verify that staff pages redirect or deny access and that customer records are private to their owner.
  4. As staff, update a product, price, stock, and delivery-zone setting; verify the storefront reflects the changes.
  5. Place a low-value test order. Confirm that the stored order total is calculated from database prices, stock decrements once, and the customer can see only their own order.
  6. Test a quote request, staff quote, customer acceptance/conversion, and the resulting order link.
  7. Test a credit-account adjustment and verify the limit rules and ledger record. Use test accounts only.
  8. Upload a non-sensitive test invoice and verify private access, queued status, and clean removal/retention behavior.
  9. Review Supabase logs, RLS policies, Auth redirect settings, Storage policies, and production error handling before launch.

Useful checks before pushing

  • Review git status and the complete diff; avoid committing local credentials or generated private data.
  • Run git diff --check and a link/reference check for the static HTML pages.
  • Open key mobile and desktop pages in a browser and test sign-in, checkout, admin navigation, and form error states.
  • Run migrations against a disposable/staging Supabase project first. The current code repository does not include an automated migration/test harness.

Go-live checklist

  • Database Migrations applied, policies reviewed, owner role assigned securely, backup/restore plan tested.
  • Security No service-role key in the browser or repository; RLS and Storage access tested with customer and staff accounts.
  • Commerce Real prices, inventory, zones, and order notifications confirmed; payment methods accurately explained to customers.
  • Automation n8n workflow tested using synthetic invoices; no production webhook secret exposed in frontend files.
  • Operations Production hostname, HTTPS, Auth redirects, email delivery, support contact, and recovery procedures checked.

This handbook is an implementation guide, not a penetration test, financial audit, or guarantee that external services are configured. Recheck the live project before accepting real customer data or payments.
